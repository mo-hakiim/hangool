Notes and assumptions

Rules from the brief and how the schema enforces them

  • Many roles per user: user_roles is the join between users and roles. Only a user holding the owner role may insert or revoke rows (database policy). assigned_by records the owner. Role codes: owner, manager, finance, accountant, hr, procurement, storekeeper, project_manager, site_engineer, site_supervisor, qs, architect, marketing, client. Revoked roles get revoked_at and stay in the table for history.
  • Nobody approves their own request: each approval step stores requested_by and approver_id, and a check requires them to differ. If the only person holding required_role_id is the requester, the step is saved as skipped and the request moves to the next step_order. A step left empty because nobody holds the role yet (for example project manager today) is skipped the same way, so it switches on once someone is given the role.
  • Audit log: database triggers write one audit_log row for every insert, update, approval decision and user_roles change, with old and new values as JSON. table_name + record_id can point at any table, so the only line drawn is to the acting user.
  • BOQ is the budget: a stage's budget is the sum of quantity × unit_price over that stage's approved boq_items. stages.budget_amount is a cached copy of that sum. A material request is checked line by line against its boq_item_id and the stage total, and the result is stored in within_budget.

Assumptions

  • No separate BOQ header table. BOQ versions live on boq_items.boq_version. A BOQ approval points to the project (entity_table = 'projects') and stores the version in approvals.ref_version. The owner's profit is stored as projects.profit_pct.
  • Approvals are polymorphic. entity_table + entity_id point to the record being approved, so the dotted lines show which tables can be approved rather than real foreign keys. Besides the six types in the brief, I added leave and purchase because the portal summary lists leave approvals and an owner or finance sign-off on purchases.
  • Two-approval payments: the threshold the owner sets is an app setting (a key–value settings table, not drawn). Payments above it get two approval steps: finance, then owner.
  • Clients log in as users. A client has a users row with the client role, linked by clients.user_id. users.totp_enabled is required for staff and the owner and not used for clients.
  • One store location. inventory_items.qty_on_hand is kept up to date from stock_movements and cannot go below zero. Stock in links to the purchase order and supplier; stock out links to project, stage and material request. Recording a delivery also sets the purchase order to delivered.
  • One attendance table covers daily labourers and staff: each row has either labourer_id or employee_id. Labourers are not system users.
  • One invoice per stage milestone (invoices.stage_id is unique). The first deposit is a payments row with payment_type = 'deposit' linked to the contract. Each payment has exactly one receipt, which cannot be edited and can only be cancelled through an approval.
  • Payment methods: sifalo_pay, zaad, edahab, evc, cash, bank. Gateway payments store the Sifalo transaction id in gateway_ref. Staff enter cash and bank payments by hand.
  • Photos and files (report photos, drawings, documents) are stored in file storage and referenced as URLs in text[] columns, not in a separate photos table.
  • Drawings: each version is its own row, linked to the version before it by previous_version_id. Once approved it is locked (is_final, locked_at) and older versions are marked superseded.
  • "Lines to users" can be switched off to declutter: most tables have an actor column (recorded_by, created_by and so on) pointing to users, and those lines dominate the full view. The FK columns stay in the tables either way.
  • Marketing inbox: still an open question, so WhatsApp and website inquiries are only recorded as leads. messages is the client portal thread between a client and staff.
  • Every table also has created_at and updated_at, left off the diagram to save space. Money is numeric(12,2) in a single currency (USD).
